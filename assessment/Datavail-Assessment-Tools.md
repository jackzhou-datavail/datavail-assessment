## 1. Overview

### What it is

A three-page dashboard scoring how closely a Databricks workspace
follows documented Databricks practice. It reads from the
`assessment.results` tables, which are produced by the assessment
collector running 42 checks derived from a 78-pattern library.

### Where the numbers come from

```
patterns/*.md            78 documented patterns and anti-patterns
      |
assessment/registry.yaml severity, weight, tier, target/floor per pattern
      |
assessment/checks.py     42 SQL checks over system.* tables
      |
assessment.results.*     6 Delta tables: run, registry snapshot,
                         check_result, check_finding, category_score,
                         assessment_score
      |
this dashboard           8 datasets, 3 pages, 18 panels
```

### The two numbers that matter

Every score on this dashboard is paired with a **coverage** figure.

- **Score** — weighted mean conformance across checks that could be
  measured. Weighted by severity: CRITICAL 5, HIGH 3, MEDIUM 2, LOW 1.
- **Coverage** — how much of what *should* have been assessed actually
  was, as a share of weight.

A check resolves to one of four states: `MEASURED` (produced a
percentage), `NOT_AVAILABLE` (the data could not be read — with a
reason), `NOT_APPLICABLE` (nothing of that kind exists here), or
`ERROR`.

Grades use two thresholds against each pattern's own target and floor:

| Grade | Meaning |
|---|---|
| GOOD | score ≥ 80 |
| FAIR | 60 ≤ score < 80 |
| POOR | score < 60 |
| INSUFFICIENT DATA | coverage < 40%, regardless of score |

### Current run at a glance

```
OVERALL 57.5 / 100   coverage 40.1%   confidence MEDIUM   critical gaps 2
MEASURED 28 · NOT_AVAILABLE 41 · NOT_APPLICABLE 9 · ERROR 0
```

### Internal notes — overview

- **Coverage is 40%.** The score describes well under half the platform.
  Never present the 57.5 without the 40.1 next to it.
- **Single run, no trend.** Nothing on the dashboard shows change over
  time yet, because only one run exists.
- **Viewer credentials.** Published with `embed_credentials: false`, so
  each viewer queries as themselves and needs `SELECT` on
  `assessment.results`. A viewer without that grant sees empty panels,
  not an error banner.
- **Paired checks double-count.** Five pattern pairs share a single
  underlying measure by design (positive and anti-pattern framings of
  the same thing). They appear as two rows/bars with identical numbers:
  `personal-identity-in-production` / `service-principals-for-automation`,
  `cost-attribution-tagging-and-budgets` / `untagged-unmonitored-spend`,
  `infrastructure-as-code-terraform-and-bundles` / `manually-configured-workspaces`,
  `task-dependencies-over-schedule-chaining` / `schedule-chained-jobs`,
  `models-in-unity-catalog` / `legacy-workspace-model-registry`.
  If a client asks why a finding appears twice, that is why. They share
  a `root_cause` key in the registry so a report can roll them up.
- **No check has a cost figure attached.** The dashboard says spend is
  unattributable; it cannot say spend is too high.

## 2. Page 1 — Onboarding Scorecard

The executive page. Opens with a text block explaining the score/coverage
pairing, then four KPIs, two bar charts and the category table.

### 2.1 Onboarding Score (KPI)

**At a glance.** The headline number, 0–100. Weighted mean conformance
across every check that produced a measurement.

**In detail.** Each measured check contributes `weight × conformance_pct`,
summed and divided by total measured weight. A CRITICAL check at 0%
drags far harder than a MEDIUM at 0%, because its weight is 5 against 2.
Checks that could not be measured are excluded entirely rather than
counted as zero — counting them as zero would punish the workspace for
the tool's blind spots.

*Current value: 57.48.*

**Internal notes.** Excluding unmeasured checks cuts both ways: it is the
honest choice, but it means the score is computed from a biased sample —
specifically, the checks that happen to be SQL-measurable. Those skew
toward compute, cost and metadata, and away from security, networking and
Git practice. Do not describe this as "the platform's score"; it is "the
score across what we could measure."

### 2.2 Measurement Coverage (KPI)

**At a glance.** The share of applicable pattern weight that produced a
real measurement. The credibility qualifier on every other number.

**In detail.** Computed as measured weight ÷ applicable weight, where
applicable excludes patterns ruled out by scope (no ML workloads, single
workspace, and so on). Confidence bands: HIGH ≥ 70%, MEDIUM ≥ 40%,
LOW below.

*Current value: 40.08% — MEDIUM, barely.*

**Internal notes.** 40.1% is one tenth of a point above the MEDIUM floor.
A single check flipping to `NOT_AVAILABLE` on the next run would drop
this to LOW confidence. Do not build a narrative on "medium confidence"
being stable.

### 2.3 Overall Implementation (KPI)

**At a glance.** The score expressed as a word: GOOD, FAIR, POOR or
INSUFFICIENT DATA.

**In detail.** Applies the grade bands to the overall score, with the
coverage floor checked first — below 40% coverage the grade reads
INSUFFICIENT DATA no matter how high the score.

*Current value: POOR (57.5, coverage just above the floor).*

**Internal notes.** This is the panel most likely to start an argument.
It reads POOR by 2.5 points. Coverage is 0.08 points above the
INSUFFICIENT DATA threshold, so the workspace is one marginal check away
from this tile saying something completely different. Be ready to explain
the bands rather than defend the word.

### 2.4 Critical Gaps (KPI)

**At a glance.** Count of CRITICAL-severity checks graded POOR. The
shortest possible remediation list.

**In detail.** Twelve patterns carry CRITICAL severity. This counts only
those that were measured *and* fell below their floor.

*Current value: 2 — `unowned-catalog-objects` (0 of 112 tables
group- or service-principal-owned) and `stale-models-in-production`
(0 of 4 experiments updated in the window).*

**Internal notes.** This number is suppressed by poor coverage. Four of
the twelve CRITICAL patterns were never measured at all —
`individual-user-grants`, `group-based-access-control`,
`account-first-identity-federation` and
`failure-notifications-and-duration-thresholds`. A client could
reasonably read "2 critical gaps" as reassuring; the honest framing is
"2 confirmed, 4 unknown."

### 2.5 Checks Measured / Not Measurable (KPIs)

**At a glance.** A pair of counts: how many patterns produced a number
(28) and how many could not (41). Nine more were not applicable.

**In detail.** Side by side they show the shape of the assessment more
directly than the coverage percentage does — more patterns failed to
measure than succeeded.

**Internal notes.** 41 versus 28 looks bad on a slide, and it is the
truthful picture. Frame it as roadmap rather than failure: the unmeasured
ones are grouped by tier on page 3, and each tier is a concrete piece of
collector work, not an unknowable.

### 2.6 Implementation by Category (bar)

**At a glance.** Weighted score per category, coloured by grade — green
GOOD, amber FAIR, red POOR, grey INSUFFICIENT DATA.

**In detail.** Seven bars, one per pattern category. Grey bars are the
important ones: the score exists but is not trustworthy.

*Current: ml-ai-lifecycle 8.9 (grey), platform-onboarding 47.1 (red),
unity-catalog-governance 61.5 (grey), orchestration-reliability 72.2
(amber), sql-analytics 74.2 (amber), table-optimization 77.2 (grey),
data-ingestion 100.0 (grey).*

**Internal notes.** **The bar ordering is visually misleading.**
`data-ingestion` renders as the longest bar at 100.0 and is grey for a
reason: it is two checks at 28.6% coverage, and one of them
(`analytics-on-raw-tables`, 455/455) is a false pass — this workspace has
no tables named bronze/raw/landing, so the layer-detection regex matches
nothing and everything trivially passes. Same problem inflates
`table-optimization` (one check) and `query-performance-fundamentals`
(14032/14032). If a client points at the 100.0 bar as a success, correct
it immediately; letting it stand is the single most misleading thing this
dashboard can do.

`ml-ai-lifecycle` at 8.9 is real but thin — three measured checks, two of
which are the stale-model proxy and gateway coverage.

### 2.7 Measurement Coverage by Category (bar)

**At a glance.** How much of each category was visible. The companion to
the panel above — read them together.

**In detail.** Bars below 40% mean the matching score bar is grey.

*Current: platform-onboarding 62.0%, orchestration-reliability 46.7%,
sql-analytics 46.0%, unity-catalog-governance 38.2%, data-ingestion
28.6%, ml-ai-lifecycle 22.0%, table-optimization 20.0%.*

**Internal notes.** Only `platform-onboarding` clears the floor
comfortably, which is why it is the only category whose grade should be
presented as a finding rather than an indication. The chart has no
reference line at 40%, so the threshold is invisible — call it out
verbally, or add a rule when regenerating.

### 2.8 Category Scorecard (table)

**At a glance.** All seven categories with grade, score, coverage,
measured count, unavailable count and POOR count. The reference table
people screenshot.

**In detail.** `n_poor` is the useful column for planning: it counts
measured checks below floor in that category, i.e. concrete work items.

*Current: platform-onboarding has 4 POOR checks — the largest single
block of confirmed, actionable findings.*

**Internal notes.** `n_not_applicable` is easy to misread as "passed."
It means nothing of that kind exists — for example `workspace-sprawl`
is N/A because this is a single-workspace account. Also note
`data-ingestion` shows `n_poor = 0`, which reads as clean but reflects
two checks, one of them a false pass.

## 3. Page 2 — Findings

The working page. Text block, then the remediation list, the
per-pattern bars, and the evidence rows.

### 3.1 Priority Remediation List (table)

**At a glance.** Every measured check graded POOR or FAIR, sorted by
severity then conformance. The worst thing at the top. This is the page
to work from.

**In detail.** Columns: severity, category, pattern title, conformance %,
grade, an `Objects` column reading `numerator / denominator unit`, evidence
row count, and the path to the pattern document so a reader can look up
the fix.

*Current: 20 rows. Top entries include `unowned-catalog-objects`
(0%, 0/112 tables), `stale-models-in-production` (0%, 0/4 experiments),
`infrastructure-as-code-terraform-and-bundles` (0%, 0/16 jobs),
`gateway-governance-for-llm-endpoints` (7.69%, 1/13 endpoints),
`untagged-unmonitored-spend` (11.12%, 781/7021 DBUs),
`documented-tables-and-columns` (16.36%, 234/1430 columns).*

**Internal notes.** The `Objects` column mixes units across rows — DBUs,
tables, jobs, columns, queries — so the numbers are not comparable
row to row even though they sit in one column. `doc_path` is a repo-relative
path, not a link; it only helps someone with the repo checked out. Three
of the 20 rows are the second half of a paired check and will look like
duplicates.

### 3.2 Conformance by Pattern (bar)

**At a glance.** All 28 measured checks as bars, coloured by grade. Bars
near zero are practices not being followed at all.

**In detail.** Useful for spotting clusters — several near-zero bars in
one category is a systemic gap rather than isolated misses.

**Internal notes.** 28 bars in one chart is cramped; labels are pattern
titles and will truncate. Two bars sit at exactly 100% and are false
passes (see 2.6). Consider splitting this by severity, or filtering to
POOR/FAIR, if you are presenting on a small screen. The chart does not
convey denominator, so a check measured on 4 objects looks identical in
weight to one measured on 14,000.

### 3.3 Evidence (table)

**At a glance.** The specific objects behind the findings — named tables,
jobs, experiments and endpoints. This is the remediation worklist, not a
summary.

**In detail.** 233 rows, sorted by metric value descending. Each row
carries the pattern, object type, fully qualified object name, owner
where known, and the measured metric.

*Examples from the current run:*
- `demos.dbdemos_modeling.billable_usage` — 65 undocumented columns
- `sandbox.hertz.hertz_clean` — 63 undocumented columns
- `/Users/nigel.silva@datavail.com/mas-eb5c1a14-dev-experiment` — 128 days since update

**Internal notes.** **This panel names individuals.** Object names include
personal workspace paths and owner emails. Check before screen-sharing,
and consider who is in the room — "Nigel's experiment is 128 days stale"
lands differently from "an experiment is 128 days stale." Evidence is
capped at 200 rows per pattern on write, so for large findings this is a
sample, not a complete inventory. Sorting by raw `metric_value` mixes
units (days, column counts) in one ordering, so the top rows are not
"worst" in any single sense.

## 4. Page 3 — Coverage & Blind Spots

The honesty page. Exists so the headline score is never mistaken for a
complete review. Do not skip it when presenting.

### 4.1 Measurement Status (pie)

**At a glance.** How the 78 patterns resolved: 28 MEASURED, 41
NOT_AVAILABLE, 9 NOT_APPLICABLE, 0 ERROR.

**In detail.** Green is measured, greys are the two non-measured states,
red would be errors. A clean run has no red.

**Internal notes.** Zero errors is genuinely good news — it means every
check that ran, ran correctly — but it is easily confused with "no
problems found." Say "no check failed to execute," not "no errors."

### 4.2 Patterns by Check Tier (bar)

**At a glance.** Why things could not be measured, grouped by the kind of
access each would need.

**In detail.** `SYSTEM_TABLE` 49 patterns (42 implemented) — plain SQL.
`WORKSPACE_API` 14 — Dashboards, Workspace/Git, Jobs settings and
`SHOW GRANTS`. `TABLE_DETAIL` 6 — needs `DESCRIBE DETAIL` per table.
`MANUAL` 6 — design judgment, requires a conversation. `ACCOUNT_API` 3 —
workspace inventory, admin roles, budgets.

Each tier is a discrete piece of work, so this panel doubles as the
roadmap for raising coverage.

**Internal notes.** The largest single win is `WORKSPACE_API` at 14
patterns — it would lift coverage more than any other tier and includes
two CRITICAL access-control patterns. `MANUAL` will never be automated;
those six require an interview and should be scoped as such in any
proposal. Seven `SYSTEM_TABLE` patterns are still unimplemented, which is
the cheapest remaining work.

### 4.3 Unmeasured Patterns (table)

**At a glance.** All 41 unmeasured patterns with the exact reason each
one could not be measured, ranked by severity.

**In detail.** Reasons fall into two kinds. Tier reasons ("Requires a
workspace API… not exposed by system tables") are structural. Specific
reasons name the object — for example
`system.data_classification.results is not readable from this workspace`,
which is why both data-classification checks are unavailable here.

**Internal notes.** This is the most defensible panel on the dashboard
and the one most likely to be skipped. It is also where scope for
follow-on work lives. Two cautions: the reason text is long and will wrap
or truncate in the table, and four CRITICAL patterns sit in this list —
if anyone quotes "2 critical gaps" from page 1, this table is the
correction.

## 5. Known issues across the whole dashboard

Consolidated for a pre-presentation check.

| Issue | Impact |
|---|---|
| Layer-detection regex (`bronze`/`gold`) matches nothing here | `analytics-on-raw-tables` and `query-performance-fundamentals` show false 100%; inflates `data-ingestion` to 100.0 |
| `always-on-oversized-warehouses` measures idleness only | Auto-stop and sizing are not in `system.compute.warehouses`; showed 100% (4/4) which means "all warehouses ran a query," not "all sized well" |
| `stale-models-in-production` uses experiment recency | Proxy for a serving-endpoint-to-training-run join that is not implemented |
| `infrastructure-as-code` detects the `[target]` bundle name prefix | Undercounts Terraform-managed jobs; 0/16 may overstate the gap |
| Five paired checks share one measure | Duplicate-looking rows and bars |
| Coverage 40.1%, 0.08 above the MEDIUM floor | Confidence band is unstable between runs |
| Evidence capped at 200 rows per pattern | Large findings are sampled, not exhaustive |
| No historical trend | Single run; no change-over-time panels |
| Units differ across rows and bars | Percentages are comparable, absolute counts are not |
| Evidence table exposes personal paths and emails | Review before screen-sharing |

## 6. Regenerating and refreshing

Re-run the collector, then refresh the dashboard in the browser — panels
read the latest `COMPLETE` run automatically, so no dashboard change is
needed for new data:

```bash
python assessment/run_via_sql_warehouse.py \
  --profile uc-semantics \
  --warehouse-id 5c7c72ebf856f7c4 \
  --results-catalog assessment \
  --lookback-days 30
```

To change panels, edit `assessment/build_dashboard.py`, regenerate, and
update in place against the same dashboard id:

```bash
python assessment/build_dashboard.py --results-catalog assessment
# then PATCH /api/2.0/lakeview/dashboards/01f1b828cc1f1b62993eafaa2c776c9f
```

Grade bands and the coverage floor are constants at the top of
`build_dashboard.py` (`GOOD`, `FAIR`, `MIN_COVERAGE`). Pattern weights and
per-check targets live in `assessment/registry.yaml`.
